# 배경지식 05. 모델 라우팅과 폴백(Model Routing / Fallback)

> **이 문서에서 다루는 큰 맥락**
>
> 프로덕션 LLM[(용어사전)](../../dict/08_ai_llm_concepts.md#llm) 앱은 하나의 모델만 믿을 수 없습니다 — 특정 모델이 다운되거나 레이트리밋에 걸리면 서비스가 멈추기
> 때문입니다. **라우팅**은 상황에 맞는 모델을 고르는 것, **폴백**은 실패 시 다른 모델로 넘기는 것입니다.
> 이 문서는 하위 개념들(오류 분류, 재시도와 지수 백오프, 서킷 브레이커, 라우터/게이트웨이, 스트리밍 페일오버)과
> 그 근간(분산 시스템의 신뢰성 패턴, FrugalGPT/RouteLLM 등), 그리고 `nanobot/providers/registry.py`와
> `fallback_provider.py` 구현으로의 연결을 다룹니다.

## 정의와 핵심 아이디어

- **라우팅(routing)**: 요청 특성(작업 종류/비용/속도)이나 설정에 따라 어떤 프로바이더/모델을 쓸지 선택.
- **폴백(fallback)**: 선택한 모델이 실패하면 대체 모델로 자동 전환.

**왜 필요한가:** LLM API는 429(레이트리밋)·5xx(서버 오류)·타임아웃·용량 초과가 흔합니다. 단일 모델 의존은
가용성을 그 모델의 SLA에 묶어 버립니다. 여러 프로바이더에 걸쳐 폴백하면 **가용성과 회복력**이 크게 올라갑니다.

중요한 관점: 이것은 LLM 고유 기술이 아니라 **분산 시스템의 신뢰성 공학**(재시도, 백오프, 서킷 브레이커, 페일오버)을
LLM API라는 새 대상에 적용한 것입니다. 다만 LLM 특유의 변수(스트리밍 중 실패, 모델별 품질 차이, 토큰 비용)가
새로운 설계 문제를 더합니다.

## 하위 개념 상세

### (a) 오류 분류(error taxonomy) — 폴백의 전제 조건
모든 실패가 폴백 대상은 아닙니다. HTTP[(용어사전)](../../dict/05_channels_gateway_ui.md#http) 오류를 두 부류로 나누는 것이 출발점입니다:
- **일시적(transient) 오류** — 429(레이트리밋), 500/502/503(서버 문제), 529(overloaded), 타임아웃, 연결 오류.
  다른 백엔드로 넘기면 성공할 가능성이 높습니다. → **폴백/재시도 대상.**
- **결정적(deterministic) 오류** — 401/403(인증/권한: 어디로 넘겨도 같은 키 문제), 400(잘못된 요청: 요청 자체가 문제),
  `context_length_exceeded`(입력이 너무 김: 다른 모델도 마찬가지거나, 줄여야 할 문제), content filter(정책 거부).
  → **폴백해도 소용없거나, 폴백하면 안 되는** 오류입니다(예: 정책 거부를 폴백으로 우회하면 안 됨).

이 분류를 안 하고 "실패하면 무조건 폴백"하면, 인증 오류를 숨기고 비용만 태우는 시스템이 됩니다.

### (b) 재시도(retry)와 지수 백오프(exponential backoff)
같은 백엔드에 짧은 간격으로 다시 시도하는 것. 간격을 1초 → 2초 → 4초처럼 **지수적으로 늘리는** 이유는,
과부하된 서버에 재시도가 몰려 상황을 악화시키는 **재시도 폭풍(retry storm)** 을 막기 위해서입니다.
여기에 무작위 지연(jitter)을 더해 여러 클라이언트의 재시도 시점이 겹치지 않게 합니다(AWS의 고전적 권고).
재시도는 "같은 모델, 잠깐 기다림", 폴백은 "다른 모델로 전환" — 순서상 재시도가 먼저입니다.

### (c) 서킷 브레이커(circuit breaker)
Michael Nygard의 *Release It!*(2007)이 정식화한 패턴. 전기 차단기처럼:
- **Closed(정상)**: 요청이 그대로 흐름. 실패를 세다가 임계치를 넘으면 →
- **Open(차단)**: 일정 시간(cooldown) 동안 그 백엔드를 **시도조차 하지 않고** 대체 경로로 직행.
- **Half-open(반개방)**: cooldown 후 시험 요청을 흘려보고, 성공하면 Closed로 복귀.

**왜 필요한가:** 죽은 백엔드에 매 요청마다 타임아웃(수십 초)을 기다리는 것 자체가 장애입니다.
"당분간 포기"를 명시적 상태로 만들면 지연이 즉시 줄고, 죽은 서버의 회복도 방해하지 않습니다.

### (d) 라우터/게이트웨이 계층
LiteLLM, OpenRouter 같은 도구는 여러 프로바이더를 **하나의 OpenAI 호환 API 뒤로** 추상화하고
라우팅/폴백/비용 추적을 대신해 줍니다. 애플리케이션 내장 폴백(nanobot 방식)과 외부 게이트웨이 방식은 트레이드오프입니다:
내장은 의존성이 없고 세밀한 제어(스트리밍 상태 인지)가 가능하며, 게이트웨이는 여러 앱이 정책을 공유할 수 있습니다.

### (e) 품질/비용 기반 라우팅
가용성이 아니라 **경제성**을 위한 라우팅도 있습니다: 쉬운 질문은 싼 모델로, 어려운 질문만 비싼 모델로.
FrugalGPT(2023)는 "싼 모델부터 시도하고 답의 신뢰도가 낮으면 상위 모델로 캐스케이드"하는 전략으로 비용을 크게 줄였고,
RouteLLM(2024)은 선호 데이터를 학습한 라우터로 GPT-4 수준 품질을 유지하며 비용을 절감했습니다.
(nanobot의 폴백은 가용성 지향이며, 이런 품질 기반 라우팅은 쓰지 않습니다 — 대신 model preset으로 용도별 수동 선택을 지원.)

### (f) 스트리밍 페일오버의 함정
스트리밍(토큰 단위 전송) 중 실패는 특별히 까다롭습니다: 이미 절반의 답이 사용자 화면에 나갔는데
폴백 모델로 처음부터 다시 생성하면 **중복/모순된 출력**이 보입니다. 실무 규칙은
"**사용자에게 내용이 나가기 전**에는 자유롭게 폴백, 나간 후에는 폴백 금지(또는 이어쓰기 같은 특수 처리)"입니다.

## 개념 간 관계

```text
오류 분류 (무엇이 일시적인가?)
    │ 일시적 오류에만
    ▼
재시도 + 지수 백오프 (같은 모델, 잠깐 대기)     ←— 분산 시스템 고전 패턴
    │ 그래도 실패하면
    ▼
폴백 (다른 모델/프로바이더로 전환)
    │ 반복 실패가 쌓이면
    ▼
서킷 브레이커 (한동안 primary 우회)             ←— Nygard, Release It!
    │ 제약 조건
    ├─ 스트리밍 페일오버 (내용이 나간 뒤엔 금지)
    └─ 결정적 오류 (인증/정책/컨텍스트 초과 → 폴백 금지)

별개 축: 품질/비용 라우팅 (FrugalGPT, RouteLLM) — 실패 대응이 아니라 경제성 최적화
```

- 폴백은 [09](../09_providers.md)의 프로바이더 추상화가 전제입니다 — 모든 백엔드가 같은 인터페이스여야 갈아끼울 수 있습니다.
- `context_length_exceeded`를 폴백하지 않는 이유는 [02](02_context_compression.md)의 압축이 올바른 해법이기 때문입니다.

## 최신 동향

- LiteLLM/OpenRouter 같은 **라우터/게이트웨이**가 다중 프로바이더 추상화를 제공.
- **서킷 브레이커** 패턴으로 죽은 백엔드를 일시 우회.
- 비용/지연 기반 라우팅, 품질 기반 라우팅(RouteLLM 계열) 등 정책 다양화.
- 프로바이더 측 자동 폴백(예: 지역 간 라우팅)과 클라이언트 측 폴백의 역할 분담 논의.

## nanobot에서의 실제 구현

### 프로바이더 레지스트리 — `providers/registry.py`
[09](../09_providers.md) 참고. `ProviderSpec` 하나에 프로바이더의 특성(키워드/키/백엔드/기본 base 등)을 선언하고,
`find_by_name`/`create_dynamic_spec`으로 조회·동적 생성합니다. 새 프로바이더 추가는 "PROVIDERS에 Spec 추가 +
config 필드 추가"면 끝(파일 상단 주석) — **데이터 주도 라우팅**의 기반이자, 위 (d)에서 말한
"내장 방식"을 가볍게 유지하는 장치입니다.

### 폴백 — `providers/fallback_provider.py`
`FallbackProvider`가 요청 범위 페일오버를 구현합니다([09](../09_providers.md)에서 상세). 핵심 정책:
- **폴백하는 오류**: `timeout`, `connection`, `server_error`, `rate_limit`, `overloaded` — 위 (a)의 일시적 오류.
- **폴백하지 않는 오류**: `authentication`/`permission`/`content_filter`/`context_length`/`invalid_request`
  — 위 (a)의 결정적 오류(넘겨도 소용없거나 넘기면 안 되는 것).
- **서킷 브레이커**: primary 연속 실패 임계치(`_PRIMARY_FAILURE_THRESHOLD = 3`)를 넘으면 일정 시간
  (`_PRIMARY_COOLDOWN_S = 60`) primary를 건너뛰고 fallback을 곧장 사용 — 위 (c)의 Closed→Open→(시간 경과 후 재시도)
  구조의 경량 구현.
- **스트리밍 안전장치**: 이미 content가 사용자에게 스트리밍된 뒤에는 폴백하지 않음(중복 출력 방지). 단 타임아웃
  stall은 새 세그먼트에서 복구 가능 — 위 (f)의 실무 규칙 그대로.
- **재귀 방지**: fallback이 또 fallback을 부르는 연쇄 차단.

### 기반의 재시도 — `providers/base.py`
폴백 이전에, 각 프로바이더는 `base.py`의 재시도 로직으로 일시적 오류를 먼저 흡수합니다(`_CHAT_RETRY_DELAYS =
(1, 2, 4)` — 위 (b)의 지수 백오프, `_TRANSIENT_ERROR_MARKERS`, 재시도 불가 429 토큰 구분). 즉
**재시도(같은 모델) → 폴백(다른 모델) → 서킷 브레이커(잠시 우회)** 의 다층 방어로, 위 관계도의 흐름과 일치합니다.

**정리:** nanobot은 데이터 주도 레지스트리로 프로바이더를 라우팅하고, 오류 종류를 세밀히 분류한 폴백 +
서킷 브레이커로 가용성을 확보합니다. "아무 때나 폴백"이 아니라 "폴백해도 되는 오류만" 넘기는 절제가 특징이며,
이는 분산 시스템 신뢰성 패턴(오류 분류 → 백오프 재시도 → 페일오버 → 서킷 브레이커)의 교과서적 적용입니다.
